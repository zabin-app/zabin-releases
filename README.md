# zabin-app/zabin-releases

This repository is the public release surface for [Zabin](https://github.com/zabin-app/zabin): prebuilt binaries, an installer script, a PM skill archive, and a multi-arch Docker image for the private `zabin-app/zabin` source. It is public so the binaries, the skill zip and the image can be downloaded without credentials; the source they are built from stays private.

**Everything here is generated.** This repository's content (this file, `install.sh`, `.github/workflows/release.yml`) is a verbatim sync of `zabin-app/zabin`'s `release/` directory, pushed by that repository's `.github/workflows/release-dispatch.yml` on every `vX.Y.Z` tag push. Do not edit these files directly here — edit `release/` in `zabin-app/zabin` and push a tag; your edit will be synced and a new release built from it.

## Install

### Prebuilt binary

```bash
curl -fsSL https://raw.githubusercontent.com/zabin-app/zabin-releases/main/install.sh | bash
```

That URL is this repository's default branch, which every tag push re-syncs, so it always serves the newest installer regardless of whether the newest release is a pre-release (GitHub's `releases/latest/...` URLs resolve only once a non-prerelease release exists). To fetch the installer that shipped with a specific release instead, use the tag-pinned asset URL that the release page prints: `https://github.com/zabin-app/zabin-releases/releases/download/vX.Y.Z/install.sh`.

Flags (pass after `bash -s --`, e.g. `... | bash -s -- --with-server`):

- `--version vX.Y.Z` — install a specific release (default: the newest stable release, or the newest pre-release while no stable one exists)
- `--prefix DIR` — installation directory (default: `$HOME/.local`; also settable via `ZABIN_INSTALL_PREFIX`)
- `--with-server` — also install `zabin-server` (by default only `zabin-tui` and `zabctl` are installed)
- `--help` — show usage

The installer detects your OS/architecture, downloads the matching tarball and `SHA256SUMS`, verifies the checksum, and refuses to install anything if it does not match. It refuses to install as root to `$HOME/.local` unless you pass `--prefix` explicitly, and warns if the install directory is not on `PATH`. Re-running it is safe (it overwrites the existing binaries).

### Verifying a download by hand

Every release publishes a `SHA256SUMS` file alongside the binaries. To verify a tarball yourself:

```bash
curl -fsSLO https://github.com/zabin-app/zabin-releases/releases/download/vX.Y.Z/zabin-X.Y.Z-linux-amd64.tar.gz
curl -fsSLO https://github.com/zabin-app/zabin-releases/releases/download/vX.Y.Z/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

(`shasum -a 256 -c --ignore-missing SHA256SUMS` on macOS.)

### Docker

```bash
docker run -d --name zabin \
  -v zabin-data:/var/lib/zabin \
  -p 127.0.0.1:2222:22 \
  -p 127.0.0.1:50051:50051 \
  -p 127.0.0.1:50052-50054:50052-50054 \
  -e ZABIN_SSH_AUTHORIZED_KEYS="$(cat ~/.ssh/id_ed25519.pub)" \
  ghcr.io/zabin-app/zabin:latest
```

The image publishes a multi-arch (`linux/amd64` + `linux/arm64`) manifest. `latest` tracks the newest non-prerelease tag; pin `ghcr.io/zabin-app/zabin:X.Y.Z` for a specific release.

## Assets published with every release

| Asset | Contents |
| --- | --- |
| `zabin-X.Y.Z-linux-amd64.tar.gz` | `zabin-server`, `zabin-tui`, `zabctl`, `LICENSE` — Linux x86_64 |
| `zabin-X.Y.Z-linux-arm64.tar.gz` | Same, Linux aarch64 |
| `zabin-X.Y.Z-darwin-arm64.tar.gz` | Same, macOS Apple Silicon |
| `zabin-pm-X.Y.Z.zip` | The `zabin-pm` project-manager skill (see below) |
| `SHA256SUMS` | One checksum line per tarball and per zip, filename only |
| `install.sh` | This directory's installer script |

Each tarball and the zip also ship an individual `<file>.sha256`, and both carry a [build provenance attestation](https://github.com/zabin-app/zabin-releases/attestations) generated by the release workflow.

## The PM skill (`zabin-pm-X.Y.Z.zip`)

A project manager who wants to watch the pipeline from their own AI desktop agent (Claude.ai, Claude Desktop, or another [agentskills.io](https://agentskills.io)-compatible host) downloads `zabin-pm-X.Y.Z.zip` from the release page and uploads it as a **custom skill** in the host's Chat/Skills settings. The zip's root folder is `zabin-pm/`; its own `README.md` and `SKILL.md` — installed with it — are the authority on what it does and how to connect it to a running Zabin server's PM MCP surface (`hosts.md` inside the skill covers host setup).

## Docker quickstart

See the [Docker](#docker) section above for the one-line `docker run`. The image bundles `zabin-server` and `zabin-tui` behind SSH; secrets (SSH keys, root password) are supplied via environment variables at container start, and the pipeline database persists in the `zabin-data` volume across restarts.

## Maintainer notes

- **Tagging**: a release is built from a `vX.Y.Z` tag, optionally with a `-rc.N` suffix (e.g. `v0.2.0-rc.1`), pushed to `zabin-app/zabin`'s default branch. `Cargo.toml` never carries the rc suffix: the tag's base version (`X.Y.Z`, with any `-rc.N` stripped) must equal `[workspace.package].version` in that repository's `Cargo.toml` — so `v0.1.0-rc.1` builds from a workspace version of `0.1.0`, not `0.1.0-rc.1`. The rc suffix (if present) marks the release a GitHub prerelease and skips the `latest` image tag; it is otherwise kept verbatim in the tag, in asset filenames, and in the image tag. `zabin-app/zabin`'s `release-dispatch.yml` enforces the match and refuses to sync/dispatch otherwise.
- **Secrets**: `SOURCE_REPO_TOKEN` (this repository) is a fine-grained PAT with `Contents: read` on the private `zabin-app/zabin`, letting `release.yml` check out the tagged source to build it, package the PM skill, and assemble the Docker build context. `ZABIN_RELEASES_TOKEN` (the *other* repository, `zabin-app/zabin`) is a fine-grained PAT with `Contents: read+write` **and** `Workflows: read and write` on this repository only — the latter is required because the token pushes to `.github/workflows/release.yml`, which GitHub refuses even with Contents write alone — letting `release-dispatch.yml` sync `release/` here and fire the `repository_dispatch`. Neither is a classic (org-wide) PAT. Never edit the synced files directly in this repository: the next tag push overwrites any direct edit without warning.
- **Running a release by hand**: normally a tag push to `zabin-app/zabin` does this automatically. To (re)run it directly against an existing tag, without waiting on a push:

  ```bash
  gh workflow run release.yml -R zabin-app/zabin-releases -f tag=vX.Y.Z
  ```

  (Add `-f publish_image=false` to skip the Docker build/push, or `-f source_repo=<owner>/<repo>` to build from a fork.)

- **Package visibility**: the `ghcr.io/zabin-app/zabin` package is created **private** the first time the `image` job pushes to it. After that first push, an org owner must flip it to Public once by hand (org Settings -> Packages) — `docker pull` otherwise fails for everyone outside the org.
- **Public logs**: this repository's Actions logs are public even though the source they build is private. The `build` job never prints or uploads raw `cargo build` output; the log shows only the `Finished` line (if the build got that far), a count of error lines, and the exit status. Dependency names, versions and file paths are never printed, and a failing build shows only an error count, never the error text itself — reproduce the build locally against the tagged source for details.
